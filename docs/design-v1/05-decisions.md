# 05-decisions

## 说明

本文件记录关键裁剪与架构决策。  
目的不是写漂亮文档，而是防止以后忘记：

- 为什么现在没做
- 不是没想到，而是故意裁掉
- 将来什么条件下再打开

---

## D-001 对话优先，结构兜底

### 决策
前台以自然语言驱动创作；后台必须维护结构化内核。

### 原因
纯聊天会失控：
- 设定漂移
- 章节与大纲断裂
- 长篇无法维护
- 阅读模式无法成立

### 影响
必须保留对象模型、决策日志、连续性状态层。

---

## D-002 V1 采用单作品工作台

### 决策
V1 先围绕单作品持续推进，不做复杂多作品管理。

### 原因
当前主风险在于：
- 对话是否能驱动创作动作
- 结构化内核是否接得住
- 阅读模式是否闭环

多作品管理会稀释验证重点。

### 未来触发
当单作品链路稳定后，再增强多作品视图与资产复用。

---

## D-003 决策日志必须是一等对象

### 决策
`DecisionLog` 为核心对象，而不是普通备注。

### 原因
没有决策日志，系统只会“回复”，不会“维护作品”。

### 影响
所有关键设定、结构变更、风格约束变更都应留痕。

---

## D-004 连续性状态单独建层

### 决策
`ContinuityState` 作为核心对象存在。

### 原因
人物状态、信息边界、持有物、伤势、身份暴露等不能散落在备注里。

### 影响
未来所有一致性检查都应围绕此层展开。

---

## D-005 V1 先用 SQLite

### 决策
V1 使用 SQLite 作为本地优先数据库。

### 原因
当前阶段是：
- 单用户
- 本地优先
- MVP / 原型验证
- 低并发

SQLite 足够且更轻。

### 迁移触发
出现多用户、Web 化、服务端任务增强时，迁移 PostgreSQL。

---

## D-006 扩展字段统一走 JSON

### 决策
V1 不对所有小说要素做强 schema，扩展字段统一走 `extensions_json`。

### 原因
题材差异大，过早全量字段化会导致模型和 UI 膨胀。

### 影响
未来需要 `field_definitions` 统一治理扩展字段。

---

## D-007 V1 只落最小八张表

### 决策
当前最小实现阶段只优先做：
- works
- characters
- outlines
- volumes
- chapters
- drafts
- decision_logs
- continuity_states

### 原因
这是最小闭环的必要骨架。

### 保留项
以下对象定义保留，但当前可暂不落表：
- relationships
- world_rules
- plotlines
- events
- foreshadows
- factions
- locations
- doc_assets
- prompt_assets

---

## D-008 不做创作 ERP

### 决策
不采用多页面重后台形态，不以表单驱动创作为主。

### 原因
用户明确希望以对话为主，不要 ERP 式软件。

### 影响
UI 应保持：
- 单工作台
- 对话流主导
- 结构侧栏辅助
- 阅读模式独立投影

---

## D-009 阅读模式是闭环，不是附属功能

### 决策
阅读模式必须保留在 V1 设计中。

### 原因
没有阅读态，系统会退化成“会写字的策划机”。

### 影响
必须支持：
- 目录
- 正文纯净视图
- 从阅读态回创作态

---

## D-010 持久化层保持薄仓储边界

### 决策
V1 的 SQLite 接入先采用薄仓储层，不把业务编排塞进 DAO。

### 原因
当前阶段要先验证最小闭环，数据库层只需要稳定承接对象持久化：
- 建表
- 基础查询
- 基础读写删除

如果过早把动作解释、状态流转、上下文组装塞进仓储层，后续会很难演化。

### 影响
- 仓储层只负责最小 CRUD 和按作用域查询
- 业务规则留在应用服务层
- 后续迁移 PostgreSQL 时，替换成本更低

---

## D-011 V1 动作层先用本地 stub 编排

### 决策
V1 的动作服务先使用本地 stub 规则生成，不直接耦合真实模型调用。

### 原因
当前阶段要验证的是：
- 最小动作链路是否成立
- 结构化对象是否能被稳定写入
- 阅读模式是否能从正文版本投影出来

如果现在把重点放到模型接入，验证焦点会被稀释。

### 影响
- `create_work_seed`
- `generate_chapter_outline`
- `draft_chapter`
- `enter_read_mode`

可以先作为本地动作跑通。后续接 LLM 时，替换生成策略，不改动作边界。

---

## D-012 V1 传输层保持最薄 HTTP 包装

### 决策
V1 先用零依赖本地 HTTP 服务包装应用服务，不提前引入复杂 Web 框架。

### 原因
当前目标是尽快把主链路动作暴露给前端或调试脚本：
- 健康检查
- 立项
- 细纲
- 草稿
- 阅读投影

这阶段不需要框架级能力。

### 影响
- 路由只覆盖 V1 主链路
- 每个请求独立打开 SQLite 连接
- 后续若需要中间件、鉴权或异步任务，再评估升级框架

---

## D-013 改写要求必须进入决策日志

### 决策
当章节细纲或正文草稿是因用户修改要求而重生成时，`decision_logs` 必须显式记录改写要求与执行模式。

### 原因
如果只改正文或章节摘要而不留痕，后续只能看到“结果变了”，却看不到：
- 为什么改
- 是先改细纲还是直接重出草稿
- 当前版本在响应哪一轮用户意图

这会削弱工作台的可追溯性，也不利于后续把对话请求稳定沉淀为结构化约束。

### 影响
- 重生成动作的 `decision_type` 和标题要与首次生成区分
- `decision` / `rationale` 要直接写出用户修改要求
- `extensions_json` 至少保留：
  - `instructionText`
  - `rewriteMode`
  - 关联章节或草稿版本信息

---

## D-014 草稿修订必须独立于首次生成

### 决策
当章节已经存在草稿版本时，后续“重写一版”“按要求改一版”应走独立的 `revise_draft` 动作，而不是继续复用 `generate_draft`。

### 原因
如果把“首次生成”和“基于已有版本修订”混在一个动作里，后续会越来越难回答：
- 这是首稿还是修订稿
- 当前版本基于哪一版产生
- 这次变化是在推进创作，还是在修改已有结果

### 影响
- HTTP 层需要单独暴露 `revise-draft`
- 草稿版本的来源关系先写入 `extensions_json`
- `decision_logs` 要区分 `chapter_draft_created`、`chapter_draft_rewritten`、`chapter_draft_revised`
