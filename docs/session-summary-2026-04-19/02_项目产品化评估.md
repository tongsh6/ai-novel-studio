# 项目产品化评估

## 评估口径

本评估采用“方向二：产品型仓库”的标准，而不是“纯内容型小说资料库”的标准。  
核心问题不是“设定写得够不够多”，而是“能否持续产出、校验、沉淀、推进整本书”。

## 当前定位判断

当前项目更准确的定位是：

`AI 小说系统的内容底座`

而不是：

`可运行的 AI 小说生产系统`

## 当前强项

### 1. 内容资产强

当前已经具备较高质量的内容层资产：

- 世界观
- 人物档案
- 关系结构
- 主线大纲
- 细纲样例
- 草稿样例
- 连续性规则
- Prompt 工具库

这意味着项目不是从零开始，而是已经具备产品化所需的“知识源”。

### 2. 创作流程意识强

仓库不是纯笔记堆积，已经能看到明显的流程拆解：

- 世界观建设
- 人物建设
- 卷纲规划
- 细纲规划
- 草稿写作
- 连续性追踪
- 决策记录

这说明产品工作流并不是凭空发明，而是可以从现有文档中抽取。

### 3. 已出现状态管理雏形

虽然还不成熟，但项目已经开始尝试把部分信息写入 JSON 状态文件，例如：

- 当前项目状态
- 角色状态
- 当前章节细纲
- 决策日志

这对后续做编排系统很关键。

## 当前短板

### 1. 没有执行内核

目前没有以下能力：

- CLI
- API
- 调度服务
- 前端界面
- 自动回写流程

所以项目还不能被称为“产品”。

### 2. 缺少统一数据模型

人物、地点、章节、伏笔、爽点、节奏、事件都没有统一 schema。  
当前仍以 Markdown 为主，系统难以稳定检索和推理。

### 3. 缺少统一事实源

现在缺少明确规则来区分：

- 正式设定
- 临时规划
- 草稿推演
- 已废弃方案

没有 canonical source，后续模型会频繁混淆。

### 4. 没有系统化的检索层

虽然文档里已经暗示需要：

- 向量化
- 知识图谱
- 状态索引

但这几层都还没有真正存在。

### 5. 没有质量门禁

当前没有自动化的：

- 连续性检查
- 节奏检查
- 人物逻辑检查
- 战力膨胀检查
- 信息泄露检查

所以即使能生成内容，也无法稳定守住质量。

## 大闭环判断

如果大闭环定义为：

`设定沉淀 -> 检索装配 -> 卷纲/细纲 -> 正文 -> 质量校验 -> 状态回写 -> 下一章继续`

那么当前项目还没有形成真正的大闭环。

当前更接近：

`设定 -> 大纲 -> 细纲 -> 草稿`

后半段明显缺失：

- 自动校验
- 自动回写
- 索引更新
- 检索增强
- 下一任务推进

结论：

- 方法论上的大闭环已经被设计出来了
- 工程上的大闭环还没有闭合

## 小闭环判断

### 已基本存在的小闭环

- 世界观建设闭环
- 人物资料建设闭环
- 大纲规划闭环
- 决策记录闭环

### 仅半成立的小闭环

- 章节生产闭环
- 状态更新闭环
- 爽点管理闭环
- 节奏管理闭环

### 尚未成立的小闭环

- 连续性自动检查闭环
- 经验积累闭环
- 人工确认闭环
- 内容索引闭环

## 当前最缺的环节

### 系统层

- 主编排 Agent
- 任务路由器
- 检索层
- 状态回写器
- 质量门禁

### 数据层

- 统一实体 ID
- 统一 schema
- 章节/人物/伏笔/事件状态模型
- canon / draft 边界

### 协作层

- 人工干预机制
- 审核节点
- 作者偏好管理
- 经验积累模块

### 产品层

- CLI 入口
- 最小工作流
- 可执行命令
- 结果存档与版本化

## 结论

这是一个“很适合产品化”的项目，但它现在仍主要停留在内容资产层。  
真正的突破点不在于继续堆设定，而在于建立：

- 编排层
- 检索层
- 校验层
- 回写层
- 人工协同层
- 经验积累层
