# 近期落地建议

## 目标

把当前仓库从“内容资产库”推进到“可运行的 AI 小说系统雏形”。

## 优先级判断

当前最不缺的是设定内容，最缺的是系统层连接件。  
因此近期开发重点不应继续扩写资料，而应优先建设下面这些能力。

## 第一阶段：建立最小产品闭环

### 目标

先跑通：

`检索 -> 章节细纲 -> 正文 -> 连续性检查 -> 状态回写`

### 必做内容

1. 定义统一数据模型
   - 角色
   - 地点
   - 章节
   - 伏笔
   - 事件
   - 项目状态

2. 明确 canonical source
   - 什么是正式设定
   - 什么是草稿
   - 什么是临时规划
   - 什么可以被系统回写

3. 建立最小状态库
   - `project_state`
   - `chapter_state`
   - `character_state`
   - `foreshadow_state`
   - `world_state`

4. 建立 CLI 入口
   - 初始化项目
   - 生成细纲
   - 写章节
   - 校验章节
   - 回写状态

## 第二阶段：建立主编排能力

### 目标

让系统开始具备“总控调度”而不只是“单次生成”。

### 必做内容

1. 主编排 Agent
2. 检索装配器
3. 任务路由器
4. 质量门禁
5. 状态回写器

### 这一阶段的交付标准

- 可以明确知道当前写到哪一章
- 可以知道下一步该做什么
- 可以根据当前状态自动拼装上下文
- 可以在生成后自动发现明显冲突

## 第三阶段：加入人工干预与经验积累

### 目标

把系统从“自动写作器”升级为“可控的协作写作系统”。

### 必做内容

1. 审核节点
2. 人工确认机制
3. 作者偏好库
4. 修改历史学习
5. 失败案例归档

### 这一阶段的交付标准

- 关键节点不再默认自动定为 canon
- 系统能识别作者常见偏好
- 系统能减少重复犯错

## 第一版建议的模块清单

- `Context Retriever`
- `Outline Planner`
- `Chapter Outliner`
- `Chapter Writer`
- `Continuity Checker`
- `State Writer`

如果资源有限，第一版不要急着做复杂前端。  
最稳的路线是：

`CLI -> 稳定状态模型 -> 主编排 -> 后续再做 Web`

## 当前最值得优先解决的具体问题

1. `main` 与 `temp` 的角色不清晰
2. 章节目录命名不统一
3. 缺少统一 schema
4. 缺少状态回写流程
5. 缺少检索入口
6. 缺少人工审核机制

## 建议的下一个实际动作

如果继续往前做，最合理的下一步是下面二选一：

### 方案 A：先做数据层

先把以下结构设计出来：

- `schemas/`
- `states/`
- `canon/`
- `drafts/`

适合先把系统边界锁死。

### 方案 B：先做 CLI MVP

先提供几个最小命令：

- `project status`
- `chapter outline`
- `chapter draft`
- `chapter check`
- `state sync`

适合尽快形成一个可运行原型。

## 结论

当前仓库最不该继续做的事，是在没有系统层的情况下继续无限扩写资料。  
当前仓库最该做的事，是先建立：

- 数据模型
- 状态模型
- 检索能力
- 回写能力
- 主编排能力

这些一旦建立，现有内容资产才会真正变成产品能力。
