# 原型验证二阶段最小内核设计

## 文档目的

本文档用于定义原型验证二阶段的最小内核范围。

它回答的不是“最终平台应该长什么样”，而是：

`为了验证二阶段方向是否成立，最少需要哪些对象模型、状态流转和工作链路`

本文档直接承接：

- [原型验证二阶段共识](./06_原型验证二阶段共识.md)
- [原型验证二阶段决策记录](./07_原型验证二阶段决策记录.md)

## 设计目标

二阶段最小内核需要证明以下 5 件事可以串起来：

1. 用户的模糊想法可以通过自由对话推进成结构化对象
2. 结构化对象可以进入某本小说的独立空间
3. 讨论结果默认先进入候选区，而不是直接生效
4. 记忆、版本、参考资产可以围绕同一小说空间持续积累
5. 局部试出的结构特性可以先在当前小说内成立，再决定是否上升

## 非目标

本轮最小内核设计不直接覆盖以下内容：

- 完整平台级多用户能力治理
- 生产级权限系统
- 完整检索与向量化方案
- 完整章节写作编排系统
- 全量 UI 交互细节
- 最终稳定 schema 的一次性定稿

## 最小验证链路

二阶段原型至少需要跑通以下最小链路：

1. 创建一个新的小说空间
2. 以自由对话方式输入模糊构思或参考作品意图
3. AI 在后台提炼出一批结构化对象和候选变更
4. 用户查看候选内容并做局部确认
5. 候选内容按指定作用域发布进入正式状态
6. 已生效内容进入小说空间的正式对象层和记忆层
7. 后续 agent 能基于这些正式内容继续给出下一步建议或候选

如果这条链路跑不通，二阶段内核视为未验证成功。

## 最小内核总览

二阶段最小内核由 5 个核心模型组成：

1. 小说空间模型 `NovelSpace`
2. 结构化对象模型 `StoryObject`
3. 候选变更模型 `CandidateChangeSet`
4. 分层记忆模型 `MemoryEntry`
5. 参考资产与结构特性模型 `ReferenceAsset` / `CapabilityFeature`

## 模型一：小说空间 `NovelSpace`

### 定位

`NovelSpace` 是二阶段的根对象。它不是单纯 project 记录，而是一部小说的长期数据底座与运行上下文。

### 最小职责

- 作为正式对象和候选对象的容器
- 承载当前讨论上下文
- 挂载记忆、版本和参考资产
- 挂载当前启用的结构特性与继承能力

### 最小字段建议

```json
{
  "id": "novel-space-001",
  "title": "未命名新书",
  "status": "ideation",
  "sourceMode": "original | assisted_by_references",
  "activeConversationId": "conv-001",
  "formalObjectIds": [],
  "candidateChangeSetIds": [],
  "memoryEntryIds": [],
  "referenceAssetIds": [],
  "enabledFeatureIds": [],
  "inheritedAuthorFeatureIds": [],
  "createdAt": "2026-04-19 12:00:00",
  "updatedAt": "2026-04-19 12:00:00"
}
```

### 最小状态

- `ideation`
- `structuring`
- `stabilizing`
- `writing_ready`

这不是产品级完整状态机，只用于判断当前小说空间所处阶段。

## 模型二：结构化对象 `StoryObject`

### 定位

`StoryObject` 是系统中的结构化事实载体。二阶段不再把核心设定直接放成大段文本，而是先落成对象。

### 最小对象类型

按已确认优先级，二阶段先支持 4 大类：

1. `novel_metadata`
2. `worldbuilding`
3. `character_relation`
4. `story_direction`

### 最小字段建议

```json
{
  "id": "obj-001",
  "spaceId": "novel-space-001",
  "type": "novel_metadata",
  "subtype": "theme | audience | hook | style_profile | constraint",
  "title": "核心卖点",
  "content": {
    "summary": "现代法医进入志怪朝堂，以验尸术撬开权力迷局",
    "tags": ["悬疑", "朝堂", "志怪"],
    "confidence": "medium"
  },
  "status": "formal | candidate | deprecated",
  "source": {
    "kind": "conversation | reference | manual",
    "refId": "conv-001"
  },
  "effectiveScope": {
    "level": "novel",
    "fromVolume": null,
    "fromChapter": null
  },
  "versionRef": "ver-001",
  "createdAt": "2026-04-19 12:00:00",
  "updatedAt": "2026-04-19 12:00:00"
}
```

### 设计说明

- `content` 暂时允许半结构化 JSON，而不是一次把每个 subtype 完全定死
- `subtype` 用来限制最小范围，但保留后续进化空间
- `status` 必须显式区分正式、候选、弃用

## 模型三：候选变更 `CandidateChangeSet`

### 定位

`CandidateChangeSet` 是候选区的基本单元。它不是单条文本建议，而是一组来自某次讨论的待确认对象变更集合。

### 最小职责

- 承接 AI 讨论产物
- 把候选内容与来源讨论绑定
- 支持整批确认或对象级确认
- 在确认时附带发布作用域

### 最小字段建议

```json
{
  "id": "ccs-001",
  "spaceId": "novel-space-001",
  "title": "第一轮小说定位与世界观候选",
  "origin": {
    "conversationId": "conv-001",
    "trigger": "ai_extracted"
  },
  "objectIds": ["obj-101", "obj-102", "obj-103"],
  "status": "open | partially_accepted | accepted | rejected",
  "visibility": "soft_visible",
  "releasePlan": {
    "mode": "future_only | from_volume | from_chapter | global_redefine",
    "volumeNumber": null,
    "chapterNumber": null
  },
  "notes": "本组候选来自自由构思阶段，不自动生效",
  "createdAt": "2026-04-19 12:00:00",
  "updatedAt": "2026-04-19 12:00:00"
}
```

### 最小操作

- `accept_all`
- `accept_selected`
- `reject_all`
- `defer`

### 设计说明

- `soft_visible` 对应已确认的“轻提示可见”
- `releasePlan` 是候选确认时必须补充的发布信息

## 模型四：分层记忆 `MemoryEntry`

### 定位

`MemoryEntry` 是二阶段的最小记忆载体。它不只是聊天摘要，而是能被后续 agent 调度和回看的结构化记忆。

### 最小层级

- `system`
- `author`
- `novel`
- `volume`
- `chapter`

### 最小类型

- `fact`
- `preference`
- `decision_reason`
- `experience_pattern`

### 最小字段建议

```json
{
  "id": "mem-001",
  "scope": {
    "level": "novel",
    "spaceId": "novel-space-001",
    "volumeNumber": null,
    "chapterNumber": null
  },
  "type": "decision_reason",
  "priority": 80,
  "summary": "本书采用慢热悬疑，不走前三章高爽强爆点路线",
  "linkedObjectIds": ["obj-001", "obj-004"],
  "linkedVersionRef": "ver-001",
  "status": "active | archived",
  "createdAt": "2026-04-19 12:00:00"
}
```

### 设计说明

- `priority` 必须显式存在，因为已确认优先级可在不同层调整
- 记忆条目必须能关联对象和版本，才能支持回看与追因

## 模型五：参考资产 `ReferenceAsset`

### 定位

`ReferenceAsset` 用于承接拆书结果。它既要能服务某本小说，也要能沉淀为作者级长期资产。

### 最小模式

- `independent_analysis`
- `project_assisted_analysis`

### 最小字段建议

```json
{
  "id": "ref-001",
  "mode": "independent_analysis",
  "ownerScope": {
    "level": "author",
    "spaceId": null
  },
  "sourceWork": {
    "title": "遮天",
    "role": "primary | secondary | parallel"
  },
  "outputs": {
    "insightIds": ["obj-r1", "obj-r2"],
    "reusableObjectIds": ["obj-r10", "obj-r11"]
  },
  "upgradeStatus": "local_only | promoted_to_author",
  "createdAt": "2026-04-19 12:00:00"
}
```

### 设计说明

- 拆书结果不直接并入小说正式对象，先作为资产存在
- 开书辅助模式下可先挂小说层，再决定是否升级到作者层

## 模型六：结构特性 `CapabilityFeature`

### 定位

`CapabilityFeature` 表示在某本小说中试出来的结构能力或元数据扩展能力。

### 典型例子

- 新的风格维度
- 新的对象 subtype
- 新的关系类型
- 新的记忆分类

### 最小字段建议

```json
{
  "id": "feat-001",
  "name": "dialogue_density",
  "description": "将风格拆出对话密度维度",
  "originScope": {
    "level": "novel",
    "spaceId": "novel-space-001"
  },
  "status": "local_trial | promoted_to_author | promoted_to_platform",
  "suggestedBy": "ai",
  "activationMode": "suggested_not_default",
  "createdAt": "2026-04-19 12:00:00"
}
```

### 设计说明

- 这类特性先在小说级试出
- 提升后也不是默认强启，只进入建议能力库

## 版本模型的最小做法

二阶段不需要完整 git-like 内容版本系统，但需要最小版本引用能力。

### 最小版本对象

```json
{
  "id": "ver-001",
  "spaceId": "novel-space-001",
  "kind": "formal_snapshot",
  "summary": "确认第一轮正式设定",
  "sourceChangeSetIds": ["ccs-001"],
  "createdAt": "2026-04-19 12:00:00"
}
```

### 版本在二阶段的职责

- 给正式对象和记忆提供引用点
- 支持未来做找回、比较、追因
- 不要求本轮就实现完整 diff 引擎

## 最小状态流转

### 1. 对话到候选

`自由对话 -> AI 提炼对象 -> 形成 CandidateChangeSet -> 轻提示可见`

### 2. 候选到正式

`用户确认全部或部分对象 -> 选择作用域 -> 生成 formal object + version snapshot`

### 3. 正式到记忆

`正式对象进入空间 -> 系统提炼记忆 -> MemoryEntry 关联对象与版本`

### 4. 局部结构到上升能力

`某本小说内试出新结构 -> 形成 CapabilityFeature(local_trial) -> 用户确认提升 -> 进入作者级建议能力库`

## 最小 API / 存储边界建议

二阶段原型不要求完整重构后端，但数据层至少应从“单一 project blob”过渡到“带对象集合”的存储方式。

### 最小存储集合建议

- `spaces`
- `objects`
- `candidate_change_sets`
- `memories`
- `reference_assets`
- `capability_features`
- `versions`

初版仍可保存在 JSON 文件中，但结构上应分集合，而不是继续只维护一个嵌套很深的 `projects.json` 单体对象。

## 最小 UI / 交互约束

虽然二阶段不以 UI 为先，但原型至少应能体现以下几个面：

1. 自由对话输入区
2. 当前小说空间摘要区
3. 候选变更轻提示区
4. 正式对象查看区
5. 参考资产查看区

不要求一开始就做复杂编辑器，但必须能看见“候选”和“正式”的区别。

## 原型成功标准

二阶段最小内核设计落地后，至少应满足以下标准：

1. 能从一次自由对话中提炼出 `novel_metadata` 或 `worldbuilding` 类对象
2. 提炼结果默认进入候选区，不直接写入正式层
3. 用户可以选择部分候选对象确认生效
4. 确认后能形成正式对象和一个版本引用
5. 正式对象可以转化出至少一条小说级记忆
6. 系统可以记录至少一个小说级局部结构特性
7. 后续 agent 能基于正式对象和记忆给出下一步建议

## 实现顺序建议

建议按以下顺序实现，而不是并行摊大：

1. `NovelSpace`
2. `StoryObject`
3. `CandidateChangeSet`
4. `Version`
5. `MemoryEntry`
6. `ReferenceAsset`
7. `CapabilityFeature`

原因是前四项先成立，最小链路就已经能跑；后两项再补，二阶段的“可进化性”才真正成立。

## 与当前一阶段原型的关系

一阶段原型并不是废弃，而是二阶段的后续工作台基础。

二阶段最小内核成立后，一阶段已有的：

- 项目管理
- 设定维护
- 章节工作区
- prompts 配置
- 自动推进流程

都可以逐步迁移到新的小说空间与对象模型之上。

也就是说，二阶段不是另起一套完全平行产品，而是在当前原型之前补上一层更早、更深的内核。
