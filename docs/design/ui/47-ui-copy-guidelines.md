## 2. 总体文案原则与系统角色设定

### 2.1 系统角色：可靠的网文编辑 / 搭档
- 系统语气应如同一个专业、严谨且服务于作者意志的编辑。
- **不要**：像一个呆板的 SaaS 后台（“执行成功”、“数据提交”）。
- **不要**：像过度热情的客服机器人（“亲爱的作者，我马上为您执行哦~”）。
- **要**：清晰、陈述事实、直接给出建议（“第三卷大纲已生成，其中发现 2 个逻辑风险，请确认是否采纳”）。

### 2.2 中国网文语境
- 全面使用中文网文行业的习惯用语，避免生硬的英文词汇直译。
- 推荐使用：立项、书名、题材、卖点、爽点、大纲、卷纲、章纲、正文、设定、伏笔、上架节点、水文警告、崩盘预警等。
- 不要直接在作者界面暴露 `long-run`、`projection_stale`、`tentative_artifact` 等底层英文词汇。

### 2.3 文案三层术语（承重定义，2026-07-22）

"产品文案"不是一类东西。所有用户可见文字按性质分三层，归层决定落点与评审标准；
新增或修改任何文案前先归层：

| 层 | 术语 | 定义 | 落点 | 改动的性质 |
|---|---|---|---|---|
| 1 | **展示文案** | 作者只读的界面文字：按钮、标签、chip、提示句、空态 | `frontend/src/lib/copy.ts`（非 prompt 字段） | 阅读体验改动；注意既有验收 driver 的文本断言联动 |
| 2 | **意图模板** | 作者点动作按钮时，系统**代作者发进对话主链的 user_message 文字**（`copy.ts` 的 `*.prompt` / `*Prompt` 字段族） | `frontend/src/lib/copy.ts` | **产品行为改动**。双重身份：以作者消息形态出现在会话（用户可见）+ 模型真实输入。评审按 prompt 工程标准：创作动词明确、产出物明确、约束明确、弱模型/确定性替身可读；不是按界面文字标准 |
| 3 | **系统口径文案** | 后端机械渲染、作为系统事实陈述展示给作者的文字：探索面渲染、app 侧 turn 事实口径、维护/审读通知 | 后端模块（如 `exploration_service`、flow 的 turn_result 构造） | 与前端同一命名口径（先例：43 §5.0.1 脉络/审读映射表）；诚实缺席不伪造；**绝不穿模型逐字输出的视觉外衣**（46 §9 红线） |

判例（2026-07-22，脉络审读批）：`reviseProsePrompt` 属第 2 层——把"针对相关章节
生成修订候选"改为"改写…正文…正文草稿…保留原稿不覆盖"是行为改动（决定模型把它
读成写作还是查账），自检标准="换真实 LLM 这仍是更好的 prompt 吗"；而"账→脉络"
改名同批贯通第 1、3 层是口径统一。

## 3. 具体文案标准

### 3.1 确认 (Confirmation) 与 采纳 (Adoption) 的术语区分
这是至关重要的区分，决定了数据是否被写入权威状态。

- **Confirmation (确认动作)**：用于确定方向或执行前放行。
  - 文案推荐：“确认开始推演”、“确认大纲方向”、“没问题，继续”。
- **Adoption (采纳动作)**：用于将 Tentative 稿件写入 Authoritative 数据。
  - 文案推荐：“采纳该卷纲”、“保存并覆盖原设定”、“收入设定集”。
  - 对于拒绝/修改：使用“废弃重写”、“提出修改意见”。

### 3.2 卡片标题规范
卡片标题应当短促，指明卡片的类型和当前对象。
- 好的例子：`需要补充细节：设定项冲突`、`大纲产物待采纳 (第一卷)`、`长跑暂停：预算不足`。
- 差的例子：`Warning_01`、`System Message`、`Card Title`。

### 3.3 风险提示与 Checkpoint 解释
当系统阻断执行或发出警告时，文案必须同时满足两点：**说明影响范围** + **给出可选动作**。

- **说明影响范围**：“发现设定冲突：刚才生成的这段对话，主角使用的武器与《设定集-武器库》中的规则不符。”
- **Checkpoint 原因解释**：“推演已暂停。预设额度已用尽（当前消耗：1200 Token），是否追加额度继续运行？”
- **动作按钮**：“[修改设定]”、“[原样采纳并覆盖规则]”、“[让助手重写该段落]”。

## 4. 验收标准约束

1. 所有示例与指导都体现了“编辑搭档”而非“客服/机器人”的语气。
2. 必须明确指导 UI 区分“确认方向”与“采纳权威数据”的文案。
3. 风险类和中断类文案明确要求说明“影响范围”与“下一步动作”，绝不可只报一个错误码或生硬单词。
4. 全文坚持面向中文网文作者进行本地化，坚决防止直接抛出英文 Contract 枚举名称至前端。

## 5. Canonical action 中文按钮映射

| `action_type` | 推荐中文按钮 | 使用场景 |
| --- | --- | --- |
| `continue_dialogue` | 继续聊这个方向 | 自由续聊、结果后继续探索 |
| `answer_clarification` | 补充说明 | clarification / 必填信息缺失 |
| `confirm_before_execute` | 确认继续 | confirmation / 高风险执行前 |
| `cancel_behavior` | 暂不继续 | 取消当前等待态 |
| `choose_candidate` | 选这个方向 | 候选方向或候选片段选择 |
| `revise_candidate` | 换一版 | 要求改写、重给候选或调整方向 |
| `identify_revision_target` | 指定要改哪里 | 作者需要指出修正对象 |
| `retry_action` | 重试 | 可恢复失败路径 |
| `narrow_scope` | 缩小范围再试 | 预算、上下文或风险过大时 |
| `open_trace_summary` | 查看原因 | trace / audit / explanation 摘要 |

## 6. 禁用词与替代表达

| 禁止直接暴露 | 推荐中文表达 |
| --- | --- |
| `projection_stale` | 阅读内容不是最新 |
| `tentative_artifact` | 待采纳产物 / 候选稿 |
| `NextAction` | 下一步建议 / 当前需要你处理 |
| `quality_finding` | 质量提醒 / 风险发现 |
| `approval_policy` | 确认规则 / 风险确认要求 |
| `checkpoint`（普通作者界面） | 暂停点 / 长跑暂停 |
| `long-run` | 长跑任务 / 批量续写 |

英文 canonical 名称只允许出现在开发、debug、trace 或文档说明里，不应直接出现在作者主界面。

## 7. 常用提示模板

### 7.1 Clarification / 探索式补槽

```text
你不需要现在就把方向想得很完整。我先根据当前设定给你三种可选推进方式，你可以选一个、混合两个，或者让我换一组。
```

```text
目前还缺少执行前必须确定的创作方向。我先帮你归纳成候选方案，确认后再开始生成，不会直接写入作品结构。
```

Clarification 文案应避免：

- “请填写核心卖点”
- “目标读者不能为空”
- “缺少必填字段”

推荐改为：

- “我们先一起找这本书最抓人的钩子。”
- “你可以不用说平台术语，我会把你的偏好整理成读者定位。”
- “我先给三种第二卷推进方向，你选更接近的一种。”

### 7.2 Confirmation

```text
确认方向：本次会重写第一卷主线，并影响后续章纲。是否继续？
```

### 7.3 Adoption

```text
卷纲候选已生成。采纳后会写入作品结构，并作为后续章节生成依据。
```

### 7.4 Checkpoint

```text
长跑已暂停：当前预算接近上限，并发现 2 个时间线风险。你可以继续运行、调整范围，或先处理风险。
```

### 7.5 Quality Warning

```text
质量提醒：这一段中主角知道了尚未公开的信息，可能影响第三章伏笔。建议先修改后再采纳。
```

### 7.6 Budget Warning

```text
预算提醒：本轮预计还需要较多 token，可能超过当前额度。请确认是否继续。
```
