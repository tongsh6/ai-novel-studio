# 作品时间线维度管理（后续需求登记）

> 登记日期：2026-10-26。
> 状态：后续需求与设计输入，尚未排期；本次不冻结 schema、ADR 或实现方案。
> 来源：作者提出“该项目后面需要加一个时间线维度的管理”，要求结合项目愿景和设计理解意图后登记。
> 同日补充澄清（意图转述）：大模型是项目核心；前章写过了几天、后章写过了两星期，后续创作时模型必须知道当前故事时间，避免因此产生连续性错误。

## 1. 意图理解

首要目标是**让创作模型在每次写作时知道当前故事时间已经推进到哪里**。前章“过了几天”、后章“又过了两星期”所建立的时间关系，需要持续保留并带入后续创作，防止时间倒退、经过时长矛盾，或人物行程、伤势、约定等仍沿用旧时点的状态。

首个真实消费者明确为**创作模型**。核心闭环为：已采纳正文中的时间表达及其参照 → 持久化、可溯源的故事时间关系 → 当前写作位置的时间上下文 → 模型后续创作 → 连续性检查与维护。

### 1.1 核心设计要求

- **跨章承接时间推进**：识别“几天后”“两星期过去了”等表达相对于哪个事件、哪条支线；同一时间线上的连续推进应累积，倒叙、并行和重复回顾分别处理。原文只有“几天”时保留不确定性。
- **写作时确实携带**：后续规划、续写和修订的实际模型输入，应按当前写作位置携带相关时点、距关键事件的经过时长、人物状态及来源；跨会话、长篇上下文裁剪或恢复后仍可重建。
- **时间与状态一起校验**：让模型据已有时间关系创作，发现时间或状态矛盾时暴露冲突与依据；时间不明时显式保留未知，必要时查证或询问作者。
- **用创作结果验证**：后续验收须核对真实模型输入与生成正文，证明模型消费了前章时间推进，且后文符合已经建立的时间约束。

### 1.2 关联管理维度

围绕上述核心，作品内时间贯穿全书、卷、章、场及人物、情节、连续性。以下为结合现有设计的延展方向，具体范围仍待后续设计确认：

- **故事时间与叙述顺序分别表达**：故事内实际发生顺序与读者读到的卷章顺序分别可查，支持倒叙、插叙和多线并行。
- **时间关系可管理**：保留时间点、持续时间、相对先后、同时发生及未知时间的表达位置；只有“次日”“三年前”等信息时，不强补精确日期。
- **事件与要素关联**：关键事件关联人物、地点、状态变化、情节线与卷章场来源；可以查看某人物或某条支线在一段时间内的经历。
- **规划与事实可对账**：区分计划发生、正文实际写出和已经推进到的位置；调整事件时间时，暴露对行程、伤势、年龄、关系、信息获知与伏笔等的影响，由作者裁决如何修订。

## 3. 后续设计应覆盖的作者场景

1. **作者强调的首要场景**：前章已写“几天后”，后章又写“过了两星期”，再续写时模型继承这段时间推进，人物回忆、约定和状态与其相容。明确量化的验证例可用同一线性时间线“过了三天”再“又过了两星期”，检查后续模型知道距起点已过十七天；原文为“几天”时不硬补具体总天数。
2. “整理这本书已经发生的关键事件，按故事内时间排一下，并标出对应章节。”
3. “第三章是倒叙，实际发生在第一章之前；检查人物经历和获知信息有没有矛盾。”
4. “把这次会面提前三天，看看两条支线、人物行程和伤势恢复会受到什么影响。”
5. “接下来写这一场时，两位角色分别在哪里、知道什么、处于什么状态？依据是哪段正文？”

上述场景是需求示例，不是固定提示词或已冻结的验收矩阵。

## 4. 进入设计时再定的事项

- 时间表达的最小粒度，以及相对时间、模糊区间、历法与多线并行的首期边界。
- 事件身份、正文来源、时点状态和版本失效/重提炼规则；章节改名或重编号不应改变事件身份。
- 创作模型如何稳定获得当前时间上下文；对话、作品档案与时间线视图如何消费同一事实源。
