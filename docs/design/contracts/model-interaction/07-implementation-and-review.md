## 2. 开工前必须回答

- 精确baseline SHA是什么？现行任务/契约是否在这之后变更？
- 每个字段由哪个现有实体产生、谁保存、谁消费、谁校验？是否能派生而非持久化？
- 规范对象是否只是视图？新增实体是否通过reuse/refactor-and-retire/truly-new/reject审查？
- 本批真正用户效果是什么？从真实工作台经过哪些边界验证？
- 对旧消费者采取何种一次性迁移/删除？不兼容历史，但作者数据的保护与重置授权是什么？
- 哪些不变量由Schema、应用、DB、实模或人工验证？不能相互代签。

## 3. 供应商不支持时的处理

真实Provider能力不满足某个必要契约时，按现役有限模式/路由失败规则处理。不得把原生工具模拟成正文XML、把截断结果接进采纳、静默丢tool_call_id或重要预算。换Provider不免除事实/引用/字节规则。工具严格Schema子集映射必须显式、独立验证，不能悄悄删限制。

## 4. 设计评审完成不等于产品完成

本包证明：JSON合法、Schema自检、合成样例正反例、自定义语义约束、参考wire形态。
尚未证明：Elixir实现能够消费、生产registry导出逐字节一致、真实Provider接受、数据库事务/权限、取消恢复、实模理解、小说质量和作者满意度。

最终完整验收仍须从同一真实页面与真实调用追溯到字段、原始响应、系统决策和实际版本，既有失败样本保留，不以降低字段范围或篡改阈值换PASS。
