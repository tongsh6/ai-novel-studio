## 完整执行步骤（一个会话必须交付）
1. 梳理全部判断工具 Schema、字段互斥、组合与版本，确保工具描述与 validator 同源，错误反馈引用实际 schema。
2. 严格核 alternative_operation_refs 等必须是 registry 真 ID；按 work/ref/版本/目标数/效果验证，拒绝“id(说明)”及虚构 observe。
3. 清晰区分 native provider response、schema_valid、effect_authorized、execution_completed、candidate_created、canon_adopted；按真实 call_id 关联，不同事实不合并为一 success。
4. 失败后 correction 不扩大原目标/预算/权限；测试 wrong-ref、跨作品、两工具非法组合、plan 组合、重复/未闭合调用。
5. 工具结果统一 envelope `{ok,data,error_code,message,retryable,observation_ref,budget_after}`；失败不得伪装成功，`retryable` 必须真实。
6. `write_candidate` 等作者可见工具 schema 必须 `additionalProperties:false`，含 `modification_scope`/`source_refs`/`coverage_note`；应用校验 target⊆observed_refs、source_refs⊆base∪observation、modification_scope 与范围一致。
7. 调用 `write_candidate` 时 `content` 必须 null；出现 `content + 候选工具` 即 `contract_violation`，不生成候选并回流有界纠错。应用解析 `tool_calls` 生成内部 `decision`，不塞给模型；`stream:true` 的 wire 必须是 SSE，完整 JSON 只作应用重组结构。
