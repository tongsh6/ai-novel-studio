# UA01 Provider Execution Stream Unification

- 状态：doing / CP4D+CP5+CP6 provider activity + scoped ProviderRun query + dialogue replay verified；ProviderExecution middle progress、chunk fact、OpenAI-compatible SSE adapter 与 Anthropic SSE adapter verified
- 类型：Agent Runtime Slice / Provider Runtime Slice / UI Contract Slice / Acceptance Slice
- 启动日期：2026-06-29

## 1. 用户 / 系统目标

提升作者体感时，provider streaming 不能作为 `complete` 之外的可选支路，也不能用“不支持则回退旧 complete 体系”的口径落地。本 slice 的完整目标是把 provider 执行统一为一套事件流架构：所有 writer / evaluator / revision / conversation / tool provider 调用最终都通过同一个 provider execution stream 产生 author-safe progress、最终输出、失败、计费和 trace 事实。

“最小 CP 点”只用于降低一次改动风险，不缩小完整 slice 范围。CP0 只审计和登记边界；后续 CP 必须继续把现有 `complete_fn` 入口迁到同一 provider execution stream，而不是并行保留一套 streaming path 与一套 complete path。

## 2. 开工检查

- Contract: `docs/design/contracts/UA-01-unified-agent-run-loop-contract-pack.md`；后续需要冻结 `ProviderRun` / `ProviderEvent` / `ProviderOutput` 等价契约，并纳入 `AgentEvent.provider_progress` 的 author-safe 投影。
- Invariant: provider 执行只能有一套运行时架构；应用层不得新增 `supports_streaming=false -> complete` 或旧体系替代分支；不得把 CP6 checkpoint progress 宣称为 token streaming；replay 不重新调用 provider。
- Boundary: CP0 只改 `tasks/`、`docs/design/contracts/`、`docs/project-ledger.md`。后续 CP 会切穿 `novel_agent`、`novel_application`、`novel_common`、`novel_web`、`frontend`、`quality`；CP0 不改 adoption / projection / memory。
- Consumer: 第一个真实消费者是 `WorkspaceChannel` / `WorkspaceChat` 的 author-safe provider activity，以及所有现有 `complete_fn` provider 调用链。
- Proof: CP0 以当前代码审计、任务索引、contract 口径和轻量检查证明方向登记正确；后续 CP 需要后端测试、Channel/UI 测试、provider trace 反证和真实 Tauri summary。
- Acceptance Driver: 目标场景登记为 `agent-provider-execution-stream-unified`，由外部自动化驱动真实 Tauri 工作台；产品代码不得新增验收感知逻辑。CP0 不新增 runnable scenario。

## 9. 试行反馈

- “最小实现步”只能是 CP 粒度，不得把完整 slice 的 architecture 和验收标准缩小为“先做一点 streaming callback”。
- CP6 既有 `agent-provider-streaming-progress` 名称容易误导；已新增 `agent-provider-execution-stream-unified`，用真实 Tauri summary 证明普通对话 ProviderExecution facts 投影，而历史 `agent-provider-streaming-progress` 仅保留为 CP6 progress/cancel/read-only batch 证据。
- 后续若继续提升体感，应继续在同一 ProviderExecution runtime 内推进真实 live vendor 验证矩阵，以及把更多创作 profile 的 provider flow 与作者可理解的计划/修订因果进一步打通；OpenAI-compatible / DeepSeek / LM Studio / Anthropic wire-level SSE、ProviderExecution cancellation、scoped ProviderRun 查询 API、同一对话流 replay UI、prepared/dispatched/response_received 中间进展、chunk 事实和前端模型执行流均已验证，不新增第二套 streaming API。
- 链路纯化已经清掉 `Provider.Execution.dependency()` / `Execution.complete_fn/1` 的裸函数 public API 兼容；后续若继续收口，应聚焦内部变量命名、provider callback 字段继续向 execution-result interface 迁移，以及 live vendor 验证矩阵，不得重新引入裸函数或 keyword opts 作为第二 provider 入口。
