# tasks / 任务状态与推进规则

本目录回答“现在做什么、做到哪里、还缺什么”。先读 [NEXT](NEXT.md) 选择工作，再进入它链接的原任务文档；不从历史记录猜队首。

## 唯一真源

| 信息 | 唯一维护位置 | 其他文件的边界 |
|---|---|---|
| 任务执行状态、checkpoint、阻塞、剩余后果、任务决策 | 原任务文档（通常 `tasks/slices/<任务>.md`）；跨任务旧债务可定位到现有对账文档的明确小节 | 每个任务只认一个文档或小节。索引、NEXT、旅程、事实台账不复制执行状态 |
| 当前选择与后续顺序 | `tasks/NEXT.md` | 当前任务一项；候选不设数量上限，按优先级与依赖列出已有明确下一步的工作；阻塞/延期另列引用。不放完成记录、证据或未核就绪性的全量 backlog |
| 产品目标、契约、设计差距 | `docs/product/`、`docs/design/` 的原文档 | 任务引用既有目标/验收范围，不复制成第二份标准 |
| 连续体验的断点与覆盖 | `docs/product/user-journeys.md` | `closed/partial/gap/blocked` 是旅程覆盖，不能当任务状态；不维护 next/queued 或队首镜像 |
| 已发生的产品事实、历史交付、证据索引 | `docs/project-ledger.md`；原任务保留详细验证，机器证据在 `artifacts/` | 台账只记有日期的事实，不持有下一任务或活动任务进度 |
| 开放差距快照 | `reports/gap-ledger/latest.json` | 从原差距表生成；不手工改状态，不把从 NEXT 移出当销账 |

设计差距“尚未满足契约”与任务“做到哪个 checkpoint”是不同事实。一个 slice 的局部完成不能自动关闭整个 G/NEM 差距；对账任务 done 也不代表其转出项 done。

## 更新规则

1. **开工**：读 NEXT → 原任务/关联契约 → 当前代码与 WIP。待 Accepted、凭据或数据授权的限制以原文为准；排到当前任务不自动解除限制。
2. **推进 checkpoint**：只更新原任务的状态、剩余范围、决策和验证记录。无需例行改 NEXT、旅程图和事实台账。
3. **换任务或重排**：只调整 NEXT 的选择/候选/阻塞引用；原因写入受影响的原任务（跨任务裁决可写既有对账文档），不在 NEXT 累积日志。
4. **完成/转交/受阻后补位**：先按完整验收范围更新原任务。未闭环后果逐项给出承接任务或条件，不因合并、延期、移出 NEXT 而销账；转交后旧文档只留链接，执行状态由接收方维护。每完成或阻塞一项，都重新核对候选与开放清单，按依赖选择下一项并补入新就绪工作；已授权范围内的常规补位无需反复询问排期。空置当前任务前按下节复核，不能从“本批 done”推导“全仓无可推进项”；补位不自动授权新增数据写入、资源使用或产品取舍。
5. **按事实更新消费者**：只有用户体验断点/覆盖改变才更新旅程；只有交付、新证据、重要缺口或设计裁决才追加事实台账。禁止为一次小 checkpoint 强制四处改状态。
6. **检查与提交**：NEXT/状态规则变化运行 `node scripts/next_task_check.mjs`；差距源变化运行 `bash scripts/gap_ledger.sh`，比较开放 ID，意外减少必须查明。提交只包含本任务改动，保留其他 WIP。产品实现仍按 [AGENTS](../AGENTS.md) 执行原有门禁和真实页面验收，本规则不降低验收标准。

原任务顶部状态统一使用 `todo / doing / blocked / deferred / done / superseded / cancelled`；既有 `pending` 等价于 `todo`，无需全仓机械改名。设计阶段可标 doing 并注明阶段；`done` 只能覆盖已验的完整范围。原任务中的完成项和决策保留，NEXT 不保留已完成任务。

## 排期与阻塞复核

- **候选按可推进性收录，不按数量截断**：核实有明确下一步、范围与状态来源的工作，按优先级和依赖列全；每行只放任务、下一步/依赖、来源。候选来源须为 `todo/pending/doing`；`blocked/deferred` 放阻塞/条件引用，只有原文中已明确可独立推进的小节可作为候选。候选的准备步骤可先推进，不等于后续全部验收前置齐备；不能仅凭旧 `doing` 自动排入。
- **未排期不等于 blocked**：未核实就绪性、已转交或与别项重复的来源回原任务核对；不得因没进 NEXT 销账。`blocked` 必须在原任务说明阻塞原因、受影响 checkpoint、解除条件；`deferred` 必须有触发条件。作者裁决只阻塞依赖该裁决的实施，不自动阻塞只读审计、证据核查或其他独立任务。
- **当前项必须有可执行下一步**：来源须为 `todo/pending/doing`。若父任务 blocked，但存在已定义的独立 checkpoint，可在原任务小节明确其范围和状态，NEXT 精确链接该锚点。不得为了过检查把 blocked 改成 doing，或用子标题状态冒充父任务状态。
- **一个排期项只认一个状态来源**：依赖写在说明列或原任务，不把多个任务并为一条“联合状态”。同一剩余后果只保留一个承接入口；已登记的 B48 不再同时作为“B29 待登记 slice”。
- **换队首先查开放清单**：运行 `node scripts/next_task_check.mjs --open`，回查原任务与既有[全量对账](2026-10-27-design-to-execution-reconciliation.md)。输出即时派生、不落盘；父任务与 checkpoint 不按独立任务计数，未识别的历史状态须人工核对，清单不代表实现授权。
- **当前项空置需要证据**：先处理清单中的 `todo/doing` 与未识别历史文档，区分可推进、待排期、真实阻塞和条件触发；复核范围、理由与遗留承接记在既有对账任务，NEXT 只链接结论。存在可推进候选时不得留空；未覆盖全仓时只写“本次复核范围暂无可推进项”，不能泛称“无 AI 可推进项”。检查器只拦结构矛盾，不代替依赖判断。
- **历史批次与完整任务分开**：过去批次的证据不改写；完整任务仍有计划内后果时顶层不能以该批次 done 代替整体完成。剩余范围在原文明确开放状态与完成标准，链接 checkpoint 只降低单步风险，不缩小原验收范围。
- **篇幅约束不限制任务数量**：检查器保留三节结构、简表、唯一来源与可达性校验；说明文字最多 80 行/6000 字符、单行最多 6000 字符，任务表格行不计入说明总量。详细决策、日志和验收证据仍回原任务。

## 决策记录

决策写回原任务，NEXT 只留“何事待谁裁决、影响哪些任务”的引用。每项至少区分：**已核实事实、建议及代价、待裁决选项、已生效结论、实施与验证后果**。

- “完善任务/更新决策材料”授权整理、事实纠错和排期，不自动接受全部建议或把 Proposed ADR 改为 Accepted。
- 已生效结论必须有作者明确选择及日期/来源；未选择的选项继续待裁决。技术事实纠正与推荐变化不能伪装成作者拍板。
- 选项应表达不同产品效果；若两个选项只是不同实现载体，先拆清产品选择与工程方案。已决定的字节因果、权限、真实证据等不变量，不作为可以为验收通过而放宽的普通选项。
- 接受 ADR 不等于实现完成：契约、schema、代码、迁移、历史兼容、真实页面证据分别由承接任务闭合，`enforcement_gaps` 不因接受提案而自动消失。

## 周期动作

- 差距回收在开工/阶段收尾或差距源改变时执行；连续扫描次数只是复核提示，不等于逾期。巡检不作为长期队首。
- 每 3–5 个执行周期做一次 10 章级真实创作复验，状态与未验范围见 [既有对账任务的真实创作复验](slices/VS00D-G-GAP-RECONCILIATION.md#真实创作复验)。复用现有 runner，记录错误对象、错绑、越权/虚报、重试、漂移与作者负担；实模/页面/文学盲评分开留证。
- 机制工作须有领域消费者；同类问题反复出现先归并病因。协议、数据修订等完整范围仍由原 slice 承接，不为减短 NEXT 缩小任务。
